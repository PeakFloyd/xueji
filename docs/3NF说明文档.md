# 学籍管理系统数据库设计 —— 第三范式(3NF) 说明文档

## 一、系统概述

本系统是一套**学籍管理系统**桌面应用，采用 Java(Swing) + SQLite 实现，用于对系、班级、学生、课程以及学生选课情况进行管理与统计。

系统在数据库设计阶段，严格按照**关系数据库规范化理论**对数据模型进行了分析与分解，使所有关系模式都达到了**第三范式(3NF)**，从而**最大程度避免数据冗余、插入异常、删除异常与修改异常**。

本文档从 E-R 概念模型出发，逐步说明关系模式转换过程，并对每一张表给出**函数依赖分析**与**范式判定**，论证其满足 3NF。

> **范围说明**：本文档针对系统的**核心 5 张表**（系 / 班级 / 学生 / 课程 / 选修）。
> 系统后续为支持「学生 / 教师 / 管理员」三角色与 AI 查询，又扩充了 3 张表
> （`teacher` 教师、`teaching` 授课、`graduation_requirement` 毕业要求），
> 其范式论证见 [`设计说明.md`](设计说明.md) 第一节。连同系统台账 `issued_student_id`，**全部 9 张表均满足 3NF。**

## 二、概念模型（E-R 图）

系统的核心实体与联系如下：

| 实体 / 联系 | 说明 |
|---|---|
| 系 (department) | 一个学校由多个系组成；每个系有系号、系名。 |
| 班级 (clazz) | 每个系下设若干班级；班级有班号、班名。 |
| 学生 (student) | 每个班级包含若干学生；学生有学号、姓名、性别。 |
| 课程 (course) | 学校开设若干课程；课程有课程号、课程名、学分。 |
| **选修 (enroll)** | 学生与课程之间存在**多对多(m:n)**联系：一个学生可选多门课，一门课可被多个学生选修；记录选课成绩。 |

关键联系如下：
- 系 —— 组成 —— 班级：**1 : n**（一个系多个班级）
- 班级 —— 包含 —— 学生：**1 : n**（一个班级多个学生）
- 学生 —— 选修 —— 课程：**m : n**（一个学生多个课程 / 一个课程多个学生）

## 三、E-R 模型到关系模式的转换

按照 E-R 向关系模式转换的规则：

1. 每个实体转换为一张关系表，实体的属性成为关系的属性，实体的主键成为关系的主键。
2. **1 : n 联系**：将"一"方的主键并入"多"方关系，作为外键（如：班级表放入系号；学生表放入班号）。此时联系本身不单独建表。
3. **m : n 联系**：必须**单独转换为一张联系表**，主键由两端实体的主键**组合**而成（如"选修"表，主键 = 学号 + 课程号）。

据此得到以下 **5 张关系表**（主键加下划线，外键标*）：

| 序号 | 关系模式 | 主键 | 外键 |
|---|---|---|---|
| R1 | 系(**系号**, 系名) | 系号 | — |
| R2 | 班级(**班号**, 班名, 系号\*) | 班号 | 系号 → 系 |
| R3 | 学生(**学号**, 姓名, 性别, 班号\*) | 学号 | 班号 → 班级 |
| R4 | 课程(**课程号**, 课程名, 学分) | 课程号 | — |
| R5 | 选修(**学号**, **课程号**, 成绩) | 学号 + 课程号 | 学号→学生；课程号→课程 |

## 四、范式判定：逐表论证达到 3NF

> 复习定义：
> - **函数依赖**：X → Y，表示属性 X 的值能唯一确定属性 Y 的值。
> - **1NF**：每个属性都是不可再分的原子值。
> - **2NF**：满足 1NF，且**消除非主属性对码的部分函数依赖**（即非主属性完全函数依赖于码）。
> - **3NF**：满足 2NF，且**消除非主属性对码的传递函数依赖**。
> - **部分函数依赖**：非主属性仅依赖复合码的一部分。
> - **传递函数依赖**：存在 X → Y → Z，且 Z 不直接依赖码 X（Y 不是码）。

### R1 系(系号, 系名)

- **函数依赖集**：`系号 → 系名`
- 码（候选键）：`系号`
- **分析**：
  - 属性均不可再分 → **满足 1NF**。
  - 主键为**单一属性**，不存在复合主键，因此**不存在部分函数依赖** → **满足 2NF**。
  - 非主属性只有"系名"，且"系名"直接函数依赖于主键"系号"，不存在中间属性，**无传递函数依赖** → **满足 3NF**。

### R2 班级(班号, 班名, 系号\*)

- **函数依赖集**：`班号 → 班名`，`班号 → 系号`
- 码：`班号`
- **分析**：
  - **1NF**：属性原子。
  - **2NF**：主键单一（班号），**无部分依赖**。
  - **3NF**：班名、系号均**直接**依赖班号。此处**不把"系名"冗余进班级表**，而是通过外键"系号"关联到系表去取系名，从而**切断**了 `班号 → 系号 → 系名` 这一传递依赖 → **满足 3NF**。

  > 反例说明：若在设计时把表写成 `班级(班号, 班名, 系名, 系地址)`，则存在 `班号 → 系号 → 系名`、`班号 → 系名 → 系地址` 等传递依赖，导致同一系名/系地址在多个班级里重复存储（冗余），并引发修改异常——这正是本设计通过**外键引用而非冗余字段**所避免的。

### R3 学生(学号, 姓名, 性别, 班号\*)

- **函数依赖集**：`学号 → 姓名`，`学号 → 性别`，`学号 → 班号`
- 码：`学号`
- **分析**：
  - **1NF**：属性原子。
  - **2NF**：主键单一，**无部分依赖**。
  - **3NF**：姓名、性别、班号都**直接**依赖学号；"班级名""系名"等不放入本表，避免 `学号 → 班号 → 班名` 的传递依赖 → **满足 3NF**。

### R4 课程(课程号, 课程名, 学分)

- **函数依赖集**：`课程号 → 课程名`，`课程号 → 学分`
- 码：`课程号`
- **分析**：
  - **1NF**：属性原子。
  - **2NF**：主键单一，**无部分依赖**。
  - **3NF**：课程名、学分直接依赖课程号，**无传递依赖** → **满足 3NF**。

### R5 选修(学号, 课程号, 成绩)  【重点：m:n 联系表】

- **函数依赖集**：`(学号, 课程号) → 成绩`
- 码：**复合码** `(学号, 课程号)`
- **分析**：
  - **1NF**：属性原子。
  - **部分依赖检查**：
    - "成绩"只属于"某学生对某门课"，它**不能由学号单独决定**（一个学生多门课多个成绩），也**不能由课程号单独决定**（一门课多个学生多个成绩）。
    - 即：`学号 ↛ 成绩`，`课程号 ↛ 成绩`。
    - 因此"成绩"是**完全函数依赖**于复合码 `(学号, 课程号)`，**不存在非主属性对码的部分函数依赖** → **满足 2NF**。
  - **传递依赖检查**：表中非主属性只有"成绩"，它直接由复合码决定，不存在中间传递 → **满足 3NF**。

  > 需要特别说明"选修"表的必要性：学生与课程是 **m:n** 关系，无法仅靠给"学生"或"课程"表加一个外键字段来表达（那样会要么重复学生记录、要么只能存一门课）。因此按规范化理论**把 m:n 联系拆成一张独立的联系表**，主键取两端的码，成绩作为描述该联系的属性。这是达到 3NF 的关键一步。

## 五、为什么这套设计能达到 3NF（小结）

1. **每个表主键尽量单一**（系、班、学生、课程），天然避免部分依赖。
2. **凡是有传递依赖隐患的属性（如系名、班名）一律不冗余**进"多"方表，而用**外键**去引用主表，切断传递依赖。
3. **m:n 联系单独建联系表**（选修），用复合主键保证其唯一、并用外键保证参照完整性。
4. 通过数据库的**主键(PK)、外键(FK)与 NOT NULL 约束**在物理层面进一步保证数据的一致性与完整性。

由此，本系统的 5 张关系表**均满足 3NF**，有效避免了：插入异常（无法单独插入无选课的新课程）、删除异常（删除学生不会误删课程）及数据冗余。

## 六、系统实现

- **技术**：Java JDK17 + Swing GUI + SQLite（JDBC）
- **数据库**：`db/xueji.db`（由 `db/schema.sql` 首次运行自动创建）
- **分层结构**（体现软件工程分层 / 关注点分离）：
  - `entity` —— 实体类，对应表结构
  - `dao` —— 数据访问层，封装 JDBC 增删改查
  - `db` —— 数据库连接与初始化
  - `ui` —— Swing 界面层（主窗口、通用 CRUD 面板、选课统计面板）

### 运行方法

```bat
build.bat   :: 编译（JDK17）
run.bat     :: 运行图形界面
```
