# 学籍管理系统 · 设计说明(含 AI 查询层)

> 本文档在原始「3NF 说明」基础上,补充**角色化扩展表**的范式论证、**身份模型**、
> **安全性设计**、以及 **AI 查询层**的分层与取舍。目标是把"数据库设计 / 安全性 /
> 职责分离 / 技术权衡"这些**设计思想**真正用出来,而不是堆炫技代码。

---

## 〇、系统定位：前后端分离

前端由 `frontend/` 的 Next.js App Router 承载；当前只初始化工程，业务页面待对接。
独立的 `backend/` 使用 Bun/TypeScript 和 pi-agent-core 提供会话、工具循环、HTTP/SSE 接口；
`ai/tool_bridge.py` 连接已有 Python 数据能力，Java DAO 与 Python 共用 `db/xueji.db`。
原桌面界面和内嵌网页已移除；模型不再通过 Python 直接绑定本地 Ollama。

> “身份 = 主键”仅为演示模型，不是生产环境的密码验证机制；服务默认仅绑定本机。

---

## 一、数据模型(9 张表,均满足 3NF)

原 5 表见 `schema.sql` 及 `docs/3NF说明文档.md`。为支撑「学生 / 老师 / 管理员」
三角色与 AI 查询,新增 `schema_ext.sql` 的 3 张表:

| 表 | 主键 | 作用 | 3NF 论证要点 |
|---|---|---|---|
| teacher 教师 | teacher_id | 老师归属某系,用于"只看本院";管理员 = 常量教师号 T001(isa 老师) | 单属性主键→无部分/传递依赖→3NF |
| teaching 授课 | (teacher_id, course_id) | 教师与课程 m:n 的联系表 | 非主属性为空→天然 3NF;m:n 拆联系表(范式要求) |
| graduation_requirement 毕业要求 | dept_id | 各系毕业所需总学分 | 单属性主键;dept_id→required_credit 直接依赖→3NF |

### 身份模型:主键即账号(小而美)
**不设账号表。** 身份 = 业务主键:
- 输入**学号**且 `student` 表存在 → **学生**
- 输入**教师号**且 `teacher` 表存在 → **老师**;若等于常量 `ADMIN_ID=T001` → **管理员**(本身是老师)

设计取舍:
- 权限的**授予/收回随存在性自动发生**:新增学生/老师即能登录,删除即失去身份,
  无需额外的"授权/回收"代码去同步——简化了状态,减少出错面。
- 不再有 `user_account` 及其多态 `ref_id`,避免了跨表外键的复杂取舍。
- 角色由程序在**数据层判定**,不存业务字段,杜绝"该用户到底是谁"的不一致。

## 二、安全性设计(核心)

本系统的安全与完整性采用**两道防线**：**数据库层约束**（兜底，不可绕过）+ **应用层 RBAC**（细粒度）。

### 2.1 数据库层：完整性约束（第一道防线）

| 约束 | 落地 | 作用 |
|---|---|---|
| 实体完整性 | 每表主键 | 保证行可唯一标识 |
| **参照完整性** | 外键 + **每条连接**开启 `PRAGMA foreign_keys=ON` | 杜绝脏引用与孤儿数据 |
| 域完整性 | `NOT NULL` / `UNIQUE` / `CHECK` | 成绩 0~100、学分 > 0、性别限 男/女、课程名唯一、**学号 8 位数字** |
| 索引 | 外键列建索引 | 加速连接与分组统计 |
| 视图 | `v_domain_rule` / `v_student_credit` / `v_course_stat` / `v_teacher_course` | 收敛重复统计 SQL，一处修改处处生效 |
| **编号策略** | `issued_student_id` 台账 | **学号只发一次、永不复用**（见下） |

**学号策略（编号只增不复用）**：
- 学号是"智能编号"（2023 + 班级 + 序号），也是**终身标识**——外部成绩单/档案都以学号对人。
- 若把已删除学生的学号补给另一个人，历史材料就会**张冠李戴**（真实世界的严重事故）。
- 因此：`issued_student_id` 记录**历史上发放过的全部学号**；新增时校验"从未发放过"；
  **删除学生不删台账行**，学号永久占用。**空号可接受，复用才是问题。**
- 两条防线：应用层预览给出友好提示；DB 层 `CHECK`/主键作兜底。

**两条关键设计决策（严谨性）**：
1. **缺失必须显式**：视图 `v_student_credit` 的 `required_credit` 在"该系未设置毕业要求"时
   返回 `NULL`，**而非默认 0**。若默认成 0，则 0 学分的学生 `gap = max(0, 0-0) = 0`，
   会被误报为"已修满"。AI 层对 `NULL` 明确作答"尚未设置毕业要求，无法判断"。
2. **常量单一来源**：及格线只在 `v_domain_rule.pass_line` 定义一次；
   `v_student_credit` / `v_course_stat` 引用它，Python 的 `pass_line()` 也读它。
   读取失败时**显式报错**，不回退默认值——静默回退会掩盖配置缺失。
   课程名加 `UNIQUE`，使自然语言按名定位课程时映射唯一。

> **重要坑（已修复）**：SQLite 的 `foreign_keys` 是**连接级**开关且**默认关闭**。
> 仅在建库时设置一次是不够的——业务连接必须各自开启，否则外键形同虚设。
> 本系统在 `DbUtil.getConnection()` 与 `dbcore.db()` 中均显式开启。

### 2.2 应用层：RBAC 与最小权限

| 措施 | 如何落地 |
|---|---|
| **防 SQL 注入** | 所有带动态值的 SQL 一律 `PreparedStatement`(Java) / 参数占位 `?`(Python),用户输入永不拼进 SQL。 |
| **RBAC 在数据层强制** | 权限用 SQL 条件锁死,不靠 LLM/界面自觉。例:老师查自己教的课 → 视图 `v_teacher_course WHERE teacher_id=?`,非本人授课直接拒绝。 |
| **最小权限** | 学生仅查自己(`WHERE stu_id=身份`);老师仅查本院与本人授课;仅 ADMIN 可增删。 |
| **受控写入** | 新增/删除学籍:校验(班级存在/学号存在与否)→ 参数化执行;非 ADMIN 一律拒绝。 |
| **身份校验** | 登录身份须真实存在于 `student`/`teacher`,查不到即拒绝——身份可信来自主键唯一性。 |

### 越权天然拦截（已实测）

拦截结果是**结构化状态**，再由表达层用**温和措辞**转述——
既不冷漠，也**绝不含糊**（必须让人明确知道"做不到"），且**措辞按角色定制**：

| 场景 | 状态 | 回复风格 |
|---|---|---|
| 学生查别人成绩 | `DENIED` | 「张伟同学，抱歉～查看 20230002 同学的成绩涉及系统权限，我只能查询您本人的选课与成绩哦」 |
| 老师查别系人数 | `DENIED` | 「李老师，我只能查询本院（软件工程系）的数据……」 |
| **老师要名单 + 看不及格** | **`PARTIAL`** | **先给能答的**（「《数据库原理》6 人、《软件项目管理》2 人不及格」），**再说明名单不可查** |
| 问"我能查询什么" | `CAPABILITIES` | 按角色列出可做的事 + 数据范围说明 |
| 删除学号后再登录 | `NOT_FOUND` | 「我在系统里没找到这个身份的记录呢～ 麻烦确认一下学号？」 |

> 两条关键原则：
> 1. **越权显式拒绝，绝不静默改写**——否则用户会误以为看到了别人的数据。
> 2. **部分可答时不得丢弃已取到的结果**——能答的先答，做不到的再温和说明。

**称呼规范**：学生 → 「张伟同学」；老师 → 「李老师」（姓+老师）；管理员 → 「管理员王老师」（管理员本身也是老师）。

## 三、AI 查询层 分层与取舍

**目标**：自然语言问答 + 受控操作，但不牺牲正确性与安全。**核心原则**：Agent 选择工具，数据层负责权限和事实。

| 层 | 文件 | 职责 |
|---|---|---|
| Agent 会话 | `backend/src/agent.ts`、`backend/src/system-prompt.ts` | pi-agent-core 多轮推理与自定义系统提示词；模型由环境变量配置 |
| HTTP 与工具 | `backend/src/server.ts`、`backend/src/tools.ts` | Next.js 可调用的 API/SSE、能力目录、自定义工具、写入确认 |
| 桥接与作用域 | `ai/tool_bridge.py`、`ai/dbcore.py` | 每次调用重验身份、由服务端派生作用域 |
| 执行与表达 | `ai/data_layer.py`、`ai/abilities.py`、`ai/facts.py` | 参数化 SQL、角色白名单、确定性事实模板 |

**设计取舍**：
1. 数值和名单只来自 SQL + 确定性事实模板，不交模型自行计数；学分只统计及格课程，及格线来自 `v_domain_rule`。
2. Agent 只能调用已注册的业务工具；不能执行任意 SQL、命令或读取文件。权限在数据层独立校验，不信任系统提示词或用户消息。
3. 作用域从会话身份派生，工具参数不能覆盖身份；越权显式拒绝，不静默改写为其他数据。
4. 写入只先返回预览；必须由用户通过确认接口提交有效 token 才执行。重新校验身份、角色和业务约束。
5. 模型可以选择 pi-ai 支持的云服务，不再依赖本地模型或本地模型不可用时的规则路由。模型服务不可用时不伪造回答。

## 四、职责分离(软件工程思想)

- Java 保留 `entity`、`dao`、`db` 数据访问与建库逻辑。
- Bun 后端承担模型调用、会话管理和 HTTP/SSE；Python 保留 `data_layer`（作用域与执行）、`facts`（事实模板）以及桥接器。
- Next.js 前端独立位于 `frontend/`；请求协议见 [`API.md`](API.md)。
- 数据库按 3NF 拆分,避免冗余与更新异常;外键保证参照完整性。
- **建库与数据分离**：结构(`schema*.sql`)、数据(`seed_data.sql`)、建库逻辑(`init_db.py` / `DbUtil.java`)各司其职，数据可由生成器确定性复现。

## 五、运行

先运行 `python db\init_db.py` 初始化数据库，再在后端配置模型提供商与密钥（参见 `backend/.env.example` 和 [`API.md`](API.md)）：

```bat
cd backend
bun install
set PI_PROVIDER=anthropic
set PI_MODEL=claude-sonnet-4-6
set ANTHROPIC_API_KEY=你的密钥
bun dev                       :: http://127.0.0.1:8090
```

前端独立启动：`cd frontend && bun dev`（当前仅脚手架页面）。Java 可选 `build.bat` 编译（需 JDK 17）。
演示主键：学生 `20230001`、老师 `T002`、管理员（老师）`T001`；不要将该无密码身份模型直接公开到公网。
