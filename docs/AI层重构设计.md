# AI 查询层 · 重构设计

> 本文档确定 AI 查询层的下一版架构。核心一句话：
> **AI 层给足自由度（自然理解 / 自然推理）；数据层严守权限边界（按角色裁剪）。**
> 设计原则可类比手机相册权限：不是"给全部照片"，而是"只给被授权的那部分"，
> 且由**系统**强制，不靠应用自觉。

---

## 一、设计原则（三条）

1. **AI 自由，数据守界**
   LLM 可以自由地理解、规划、多轮推理；但它**没有任何直接访问数据库的能力**，
   只能提出"我想调用哪个能力 + 什么参数"。

2. **权限在数据层强制，不靠 LLM 自觉**
   角色可见范围由 SQL 条件锁死（`WHERE` 子句），LLM 与界面都无法绕过。

3. **作用域由身份注入，绝不接受 LLM 传来的身份参数**（关键）
   LLM 输出里的任何"身份类"参数一律不可信。服务端在执行时**用登录身份覆盖**，
   这类似相册选择器发的是"受限句柄"，而不是"全库 + 信誉"。

---

## 二、三道防线（防越权 / 防幻觉 / 防注入）

| 防线 | 措施 |
|---|---|
| 防越权 | 能力函数**白名单** + 执行时**强制套用身份作用域**（LLM 传的身份参数被忽略并覆盖） |
| 防幻觉 | **数字不由 LLM 产生**：一切计数/聚合/比较由 SQL 精确计算，回答用确定性模板拼装 |
| 防注入 | 全部 SQL 参数化（`?` 占位），**禁止** LLM 生成裸 SQL（不做 text-to-SQL） |

---

## 三、架构分层

```
① 上下文层  登录时按【登录身份】构建作用域快照（只含该身份可见的实体名）
            作用：让 LLM "认识" 系名/班号/课程名等实体，从而听懂并抽取参数
   ↓
② 规划层    LLM 把自然语言 → 结构化计划：能力函数 + 参数（支持一句多查 / 指代消解）
            绝不生成 SQL
   ↓
③ 执行层    按白名单能力函数执行参数化 SQL，并【强制套用身份作用域】
            RBAC 在此锁死，不可绕过
   ↓
④ 表达层    数字用确定性模板拼装（防编数）；自然语言外壳可交给 LLM
```

## 四、能力函数目录（白名单）

**学生（STUDENT）**
| 能力 | 说明 | 强制作用域 |
|---|---|---|
| `my_credit()` | 我的已修学分与毕业差距 | `stu_id = 登录学号` |
| `my_courses()` | 我的选课与成绩 | `stu_id = 登录学号` |
| `my_dept_mates_count()` | 本系同学数（不含自己） | 本系 |

**教师（TEACHER）**
| 能力 | 说明 | 强制作用域 |
|---|---|---|
| `my_teaching_courses()` | 我教的课程 | `teacher_id = 登录教师号` |
| `my_dept_students_count()` | 本院学生数 | 本院 |
| `course_avg(course_name)` | 我授课程的均分 | 必须是本人授课 |
| `course_fail(course_name)` | 我授课程不及格人数 | 必须是本人授课 |
| `my_courses_summary()` | 我授各门课的选课人数、平均分与不及格人数 | 必须是本人授课 |
| **`my_course_students(course_name)`** | **我授某课的学生名单（学号/姓名/本课成绩）** | 必须是本人授课 |
| **`my_failed_students([course_name])`** | **我授课程中不及格的学生（学号/姓名/分数）** | 必须是本人授课 |
| **`my_student_scores(stu_id/stu_name, [course_name])`** | **某学生在我所授课程中的成绩** | 整条查询锚定 `teaching.teacher_id = 本人` |

> **教师为何能看学生名单？** 现实中老师对所授课程的学生名单与**本课**成绩是可见的（教学必需）。
> 但**看不到**：该生其它课程的成绩、总学分/毕业进度、以及非本人授课的学生。
> 可见范围恰是这条连接路径能走到的数据：
> `teacher → teaching → course_id → enroll → stu_id → student(stu_id, stu_name)`。

**管理员（ADMIN，常量 T001）**
| 能力 | 说明 |
|---|---|
| `total_students()` / `total_teachers()` | 全校计数 |
| `students_by_dept()` | 各系人数 |
| `list_students()` / `list_teachers()` | 名单 |
| `student_credit_of(stu_id)` / `student_courses_of(stu_id)` | 指定学生的学业数据 |
| `add_student(...)` / `delete_student(...)` | **受控写入**（预览 → 确认 → 落库；学号只发一次） |

> 管理员是教师角色的**超集**，可调用教师能力。

| 数据范围 | 学生 | 教师 | 管理员 |

| 跨系 / 全校 | ❌ | ❌ | ✅ |
| 他人其它课程成绩、总学分/毕业进度 | ❌ | ❌ | ✅ |
| 写入 | ❌ | ❌ | ✅ |

## 六、会话与登录

- **登录即刷新**：切换身份 → 清空对话历史 + 重建作用域快照（避免跨身份串味）。
- **对话历史**：在同一身份内保留，用于"学生呢"这类指代消解。
- **作用域随身份变**，因此历史不得跨身份复用。

## 七、开销实测（RTX 4060 8G + qwen2.5:7b）

| 指标 | 实测值 |
|---|---|
| 全量数据快照 | 5324 字符 ≈ 2050 tokens |
| 预填充（读入上下文） | 0.9 ~ 1.0 秒 |
| 首次调用（含载入显存） | 7.3 秒 |
| 后续调用 | 3.2 秒 |
| 规划准确率（能力+参数抽取） | 5 / 5 ✅ |

**结论**：开销完全可接受（用户允许"加载几秒"）；上下文按角色裁剪后只会更小。

## 八、为什么不让 LLM 直接对数据推理（实测依据）

把全量数据交给 qwen2.5:7b 后，实测其**计数能力不可靠**：

| 提问 | 真值 | 模型回答 |
|---|---|---|
| 计算机科学系有多少学生 | 20 | ❌ 12 |
| CS2301 班有多少学生 | 5 | ❌ 23 |
| 同一问题再问一次 | 20 | ❌ 10（与上次不同） |

而**检索型**问题表现良好：问"某学生选了哪些课"，模型照抄全部 9 门课号，完全正确。

> 结论：**LLM 擅长理解、抽取、照抄；不擅长计数、聚合、比较。**
> 因此数字一律由 SQL 产生——这既是准确性问题，也是安全问题。

## 九、应答人格设计（温柔地拒绝，但不松口）

### 9.1 分工原则

> **数据层决定"能不能"（硬边界）；语言层决定"怎么说"（软措辞）。**

越权时不是抛一句冷冰冰的 `[拒绝] 权限不足`，而是由 LLM 用**温和、礼貌、并给出替代方案**的方式表达。
但**结论不可更改**：措辞是表面，边界是内核。

### 9.2 数据层返回结构化结果（决策在数据层）

数据层不返回"句子"，而返回**带状态的结构**，让语言层知道该怎么措辞：

| 状态 | 含义 | 语言层动作 |
|---|---|---|
| `OK` | 有事实 | 数字用确定性模板，外壳可润色 |
| **`PARTIAL`** | **一部分能答、一部分越权** | **先给能答的事实，再温和说明做不到的那部分**（绝不丢弃已取到的结果） |
| `DENIED` | 越权/不在作用域 | 温和说明限制 + **提供作用域内的替代** |
| `NOT_FOUND` | 实体不存在 | 温柔提示并请对方确认 |
| `UNKNOWN` | 无对应能力 | 说明能做什么，**严禁承诺清单外的能力** |
| **`CAPABILITIES`** | 用户问自身权限 | 列出**按角色裁剪**的能力清单 + 数据范围说明 |
| `CHAT` | 闲聊 | LLM 自由回应，**禁止罗列能力**（否则会编造） |

**`DENIED` 的措辞必须按角色定制**：同一件事对学生的说法和对老师的说法不同。
（反面教材：老师被回复"您只能查看本人的选课与成绩"——那是学生口径。）

### 9.3.1 称呼规范

| 身份 | 称呼 | 例 |
|---|---|---|
| 学生 | 姓名 + 同学 | 张伟同学 |
| 老师 | 姓 + 老师 | 李文静 → 李老师 |
| 管理员 | 管理员 + 姓 + 老师 | 王建国 → 管理员王老师 |

> 管理员本身也是老师，故称呼同时点明"管理员"身份与"X老师"称呼。

由 `dbcore.address_of()` 统一生成，随事实与拒绝措辞一起流到表达层；
**数据层给出的是"称呼"，表达层不自行拼接姓名**。

### 9.3.2 两条实测教训（务必保留）

1. **闲聊路径不要让它"说说能做什么"**：闲聊时模型拿不到能力清单，
   一旦被要求介绍能力，它会**编造**出并不存在的权限（实测出现"您可以查看学生的学习成绩、学籍信息"）。
   → 闲聊只做社交；能力清单走 `CAPABILITIES` 路径。
2. **权限类问题不要交给 LLM 判定**：它可能误判为闲聊，进而编造能力。
   → `planner.plan()` 用**关键词确定性短路** `权限/能查什么/我能做什么` → `CAPABILITIES`。

`DENIED` 需携带：`reason`（原因码）、`scope_desc`（我能看到什么）、`alternatives`（**我可以帮你做什么**）。

### 9.3 人格规格（系统提示词要点）

- **温和、礼貌**：多用"我""您"，不使用"错误 / 拒绝 / 非法 / 权限不足"这类词
- **先承接、再说明、后给替代**：三段式
  1. 承接意图（理解您想…）
  2. 说明限制（不过我这边只能看到…）
  3. 给可行替代（要不要我帮您看看…）
- **逆来顺受但不松口**：不争辩、不说教、不重复拒绝；用户再施压也只温和重申并再给替代
- **必须让对方明确知道"这事我做不到"**——不能为了温柔而含糊其辞（含糊比冷漠更糟）
- **绝不编造数据**；不知道就说不知道
- 允许**可有可无的闲聊**（打招呼、自我介绍、能做什么、道谢、告别、鼓励），且闲聊不应显得敷衍

### 9.4 示例（冷 → 暖）

| 场景 | 冷冰冰（旧） | 温和（新） |
|---|---|---|
| 学生想新增学籍 | `[拒绝] 只有管理员可新增学籍。当前角色 STUDENT` | 「抱歉哈，新增学籍只有管理员能做，我这边帮不上忙～ 不过我可以帮您看看自己的学分和选课情况，需要的话说一声？」 |
| 老师查非本人课程 | `[拒绝] 您未教授课程「高等数学」` | 「不好意思，我只能看到您本人授课的数据，《高等数学》不在您的授课列表里，所以查不了。您教的《数据库原理》我可以帮您看平均分或者不及格人数～」 |
| 身份不存在 | `身份不存在或无权` | 「我在系统里没找到这个身份的记录呢～ 麻烦确认一下学号或教师号有没有输错？」 |

### 9.5 安全保证：人格化不削弱边界（三重兜底）

1. **越权能力根本不执行** → LLM 手上压根没有越权数据，无从泄露
2. **上下文按作用域裁剪** → 即便被套话，模型上下文里也只有本人可见的数据
3. **数字只由 SQL + 模板产生** → LLM 不参与产生任何数字

因此人格化纯粹是**表现层**，安全性由数据层独立保证——即使 LLM 被"越狱"诱导，
它也没有可泄露的数据、也没有能改变结论的权限。
